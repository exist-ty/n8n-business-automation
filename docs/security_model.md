# Модель угроз (STRIDE) — Self-Service Analytics Bot

Дополняет `docs/self-service-bot-security.md` (детальный разбор трёх слоёв
защиты) систематическим разбором по STRIDE — не для того, чтобы повторить
то же самое другими словами, а чтобы проверить, не осталась ли какая-то
категория угроз вообще не рассмотренной. Одна нашлась (Spoofing — см. ниже),
и это честно отмечено как открытый пробел, а не скрыто.

Область: `workflows/06_self_service_analytics_bot.json` — Telegram → LLM
(генерация SQL) → валидация → Postgres (`n8n_selfservice`) → ответ.

| Угроза | Применимо? | Реально сделано | Статус |
|---|---|---|---|
| **S**poofing (подмена личности) | Да | **Ничего на уровне воркфлоу.** `chatId` из входящего сообщения используется только как адрес для ответа, не проверяется против allowlist доверенных чатов. Мягкая защита — сам бот должен быть добавлен только в приватный чат менеджеров (защита на уровне Telegram, не на уровне кода) | ⚠️ **Открытый пробел** |
| **T**ampering (подмена запроса / SQL-инъекция) | Да | Промпт-инъекция в вопросе пользователя ожидаема по умолчанию (см. `self-service-bot-security.md`). Code-нода `Validate SQL`: один оператор, запрет `--`/`/* */`, обязательный `SELECT`/`WITH`, чёрный список DDL/DML-ключевых слов — быстрый отказ, но обходимый в принципе (не полноценный AST-парсер) | ✅ Частично (fail-fast) + ✅ реальная гарантия ниже |
| **R**epudiation (невозможность отследить, кто что сделал) | Да | `n8n` хранит историю выполнения (execution log) с полным телом запроса и `chatId` — достаточно для расследования постфактум, но нет structured audit log с request/response в отдельной таблице | ⚠️ Частично — есть сырые логи n8n, нет структурированного аудита |
| **I**nformation disclosure (утечка данных) | Да | **Главная гарантия**: `GRANT SELECT` роли `n8n_selfservice` выдан только на 7 агрегированных витрин — `stg_customers.email`/`.name` физически недостижимы, даже если LLM сгенерирует `SELECT * FROM stg_customers`. Проверено эмпирически: `permission denied` | ✅ Реально гарантировано (роль БД, не промпт) |
| **D**enial of service | Да | `statement_timeout = '5s'` на роли — легальный `SELECT pg_sleep(999)` (не ловится GRANT-моделью, это чтение) обрывается таймаутом. Проверено эмпирически: обрыв ровно на 5-й секунде. Нет rate-limiting на уровне Telegram-триггера — серия быстрых сообщений от одного чата не ограничена | ✅ Statement-level, ⚠️ нет rate-limiting на входе |
| **E**levation of privilege (выход за пределы роли) | Да | `default_transaction_read_only = on` — блокирует `INSERT`/`UPDATE`/`DELETE` даже в обход отсутствия `GRANT` (например, через `SECURITY DEFINER`-функцию). Проверено эмпирически: `INSERT` падает с `cannot execute INSERT in a read-only transaction` | ✅ Реально гарантировано |

## Три конкретные заблокированные атаки (проверено на реальной БД, не в теории)

| Запрос | Ожидаемый результат | Фактический результат |
|---|---|---|
| `SELECT * FROM stg_customers` (попытка PII) | `permission denied` | Подтверждено — роль не имеет `GRANT` на эту таблицу |
| `INSERT INTO mart_sales_summary ...` | Блокировка на уровне транзакции | Подтверждено — `cannot execute INSERT in a read-only transaction` |
| `SELECT pg_sleep(10)` (DoS через легальный SELECT) | Обрыв по таймауту | Подтверждено — прервано ровно на 5-й секунде (`statement_timeout=5s`) |

## Явно принятые риски, не устранённые

- **Spoofing не проверяется программно** (см. таблицу выше) — исправление
  потребовало бы явного allowlist `chatId` в Code-ноде `Build prompt` до
  генерации SQL, либо ограничение видимости бота в Telegram на уровне
  BotFather/группы. Не сделано в этой версии — задокументировано как
  осознанно принятый риск пет-проекта, а не забытый пробел.
- **Rate-limiting отсутствует** — сотня сообщений подряд от одного чата
  не ограничена ничем, кроме `statement_timeout` на каждый отдельный
  запрос. При реальном продакшн-использовании это стоило бы закрыть на
  уровне n8n (Rate Limit-нода) или API Gateway перед вебхуком.
- **Чёрный список ключевых слов в `Validate SQL` в принципе обходим** —
  не претендует на полноценный SQL-парсер с whitelist AST. Это осознанно:
  реальная гарантия — не в этом слое, а в правах роли `n8n_selfservice`
  (Information disclosure/Elevation of privilege выше), которая
  физически не может ничего, кроме `SELECT` по 7 перечисленным объектам,
  даже если валидацию обойти полностью.

См. также `docs/self-service-bot-security.md` (три слоя защиты, честная
оговорка "безопасность SQL ≠ корректность ответа") и
`sql/readonly_role_selfservice.sql` (конкретные `GRANT`/`ALTER ROLE`).
